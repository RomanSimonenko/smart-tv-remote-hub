# Обновление локального приложения

Обновляй именно запущенную установку с её данными и конфигурацией.
Общие правила находятся в корневом `AGENTS.md`; здесь — порядок работы
с существующей Docker-установкой. Все пути ниже заданы от корня репозитория.

## Определи установку

1. Проверь текущий checkout, ветку и локальные изменения. Сопоставь их
   с build context работающего приложения: worktree и контейнер могут
   относиться к разным каталогам. До пересборки убедись, что выбранный
   build context содержит нужные изменения. Если нет — установи способ
   доставки в рамках задачи; не переноси автоматически чужие локальные
   изменения между checkout.
2. Через `docker compose ls --format json` найди кандидатов. У выбранного
   контейнера проверь Compose project, working directory, упорядоченный
   список config files, публикацию портов и фактический volume в `/data`.
   Выводи только необходимые поля, а не весь inspect или environment.
3. Прочитай `compose.yaml` и именно активные override-файлы. Зафиксируй
   project, config files, используемый env-файл/переменные, origin,
   host port и имя volume. Локальные имена не переноси в этот навык.
   Если кандидатов несколько и браузер/путь не определяет нужный,
   уточни выбор до изменения контейнеров.

## Проверь и обнови

- Сначала выполни узкую проверку изменений. Для UI используй существующий
  быстрый preview, если он доступен; Docker обновляй после этой проверки.
- Для тестовых изменений без изменения приложения пересборка не нужна.
- Сохраняй выбранные Compose project, config files в исходном порядке,
  env-настройки и host port при `up -d --build app`. Команда без ранее
  использованных overrides может создать другую установку или volume.
- Изменение внешнего volume, миграция данных, удаление ресурсов и выпуск
  setup-токена не являются частью обычного обновления.
- Не применяй `down -v`, prune или удаление volume для устранения ошибки
  запуска. При несовпадении mount останови дальнейшие изменения, установи
  причину и восстанови привязку к прежним данным, сохранив оба volume.
- Сопоставь после обновления фактический mount и порт с исходными.
  Проверь состояние контейнера и `/api/health` по обнаруженному origin.

## Проверь результат

Убедись, что на открытом экране нет несохранённых правок. Обнови страницу
во встроенном браузере и проверь изменённое поведение на активном приложении.
Health и сборка сами по себе не подтверждают доступность нового интерфейса.
Если браузер поймал сетевую ошибку во время рестарта, дождись готовности
API перед повторным открытием исходного URL; не обходи защитные страницы.

В результате укажи: что обновлено, какие проверки прошли, сохранён ли
прежний volume и что проверено в браузере. При неудаче различай ошибку
сборки, старый контейнер, неверную конфигурацию и ошибку самого приложения.

Подробнее о данных, origin и диагностике: `docs/docker-desktop.md`.
`pnpm test:docker` проверяет синтетическую установку; запускай его при
изменениях Docker/хранения, а не после каждой правки интерфейса.

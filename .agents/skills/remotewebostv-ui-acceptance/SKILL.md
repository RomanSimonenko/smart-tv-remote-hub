# Приёмка рабочего интерфейса

Этот навык задаёт короткий порядок приёмки RemoteWebOSTV; дизайн-правила
принадлежат корневому `AGENTS.md`, ТЗ и существующим дизайн-навыкам.
Все пути ниже заданы от корня репозитория.

## Определи критерий

- Установи экран, актуальное требование пользователя, тему, viewport
  и состояние. Отдели аудит от разрешённых исправлений: запрос аудита
  сам по себе не разрешает менять интерфейс.
- Прочитай `apps/web/PRODUCT.md`, применимый раздел
  `docs/superpowers/specs/2026-10-11-product-ui-design.md` и уточняющее ТЗ
  экрана. Найди соответствующий макет в `docs/design/mockups/2026-10-11/`.
  Приоритет: явно согласованные последующие требования → ТЗ → макет.
  Если соответствующего макета нет, обозначь это; не объявляй сравнение
  с макетом выполненным и не создавай новый дизайн без запроса.
- Используй проектный `impeccable` как основной workflow, а `ui-ux-pro-max`
  только для относящихся к задаче рекомендаций. Рабочие экраны — code-first;
  `design-taste-frontend` относится к публичным страницам. Не запускай
  генерацию новой палитры или концепции для небольшой правки.
- Повторно используй уже прочитанные в беседе инструкции и браузерную
  документацию. Не загружай все навыки и ТЗ заново на каждом проходе.

## Один проход наблюдения

Во встроенном браузере проверь текущий экран и сохрани визуальное
свидетельство. Сравни композицию, размеры, выравнивание, интервалы,
типографику, токены и иконки при сопоставимых viewport/теме/состоянии.
Для поведения проверь только затронутые элементы, клавиатуру и состояния,
которые меняются по задаче. Селекторы выбирай по текущему DOM/AX.

Не затрагивай несохранённые правки. Открытие рабочего экрана, запуск
кейса, изменения сохранённых фильтров/данных и команды ТВ могут иметь
побочные эффекты: выбирай безопасное наблюдение. Дополнительные пустые,
ошибочные и длинные состояния моделируй отдельно на синтетическом стенде
и обозначай их как синтетические; изолируй его cookies от реальной сессии.

## Исправление и проверка

Если исправления разрешены, собери относящиеся к запросу находки в один
патч владельца кода и стилей. Следуй существующим токенам и компонентам.
Проверь в существующем быстром preview, когда он доступен. При изменении
поведения запусти узкую поведенческую проверку; для косметической правки
проверь отрисовку. Выполни требуемые статические проверки. Полный набор
тестов нужен только при обоснованном риске.

Выполни ручной detector по изменённым целям согласно загруженному
`impeccable`; при аудите только сообщи подтверждённые находки. При разрешённых
исправлениях устрани относящиеся к задаче находки одним пакетом. Не объявляй
каждый автоматический сигнал дефектом без проверки на реальном экране.

Для активного Docker-preview заверши обновление и проверку по
`remotewebostv-deploy`. Не пересобирай Docker во время аудита без изменений.
Сделай итоговый снимок и проверь тот же сценарий в работающем приложении.
Дополнительный проход нужен при новом дефекте, а не для бесконечной полировки.

В результате укажи: экран, viewport/тему, проверенные состояния, применённые
навыки, визуальное свидетельство и оставшиеся расхождения/непроверенные зоны.
Для небольшой правки достаточно короткого итога; не превращай его в полный
аудиторский отчёт. Функциональный тест не заменяет визуальную приёмку.

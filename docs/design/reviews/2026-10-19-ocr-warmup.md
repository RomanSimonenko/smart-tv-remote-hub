Актуальное состояние: предварительный прогрев выполняется до открытия HTTP; готовый процесс сохраняется между успешными запросами. Ниже — исходные замеры и последующие этапы реализации.

проверочный JPEG 1674×941 из текущей вкладки. Новое фото не снималось;

времени запроса и восстановление процесса после зависания/аварии.

## Реализация постоянного процесса

После согласования пользователя процесс сохраняется после первого успешного
запроса. Идентификатор каждого запроса проходит через image/base/retry/result;
stdin остаётся открытым. Базовая и адресная модели загружаются один раз, кадр
и результаты остаются локальными для запроса. Одновременная работа отклоняется.
При отмене, ошибке, тайм-ауте или нарушении протокола процесс уничтожается;
занятость снимается после close. Следующий запрос создаёт новый процесс.
Авария между запросами замечается, остановка приложения завершает и idle-процесс.

Проверки: 22 теста протокола/жизненного цикла, 518 тестов API, сборка API/Docker,
общий typecheck, три браузерных сценария настроек и условий OCR прошли.
Независимое ревью блокирующих замечаний не выявило. Реальные модели обработали
схему снимок A → B с адресной перепроверкой → A одним процессом; два результата
A совпали полностью, маркер адресной перепроверки не перешёл на следующий кадр.

Docker без сети: 17,946 / 15,525 / 15,168 с, память процесса после запросов
456 / 496 / 496 MiB. Второй запрос загрузил дополнительную адресную модель.
Этот замер частично пересекался с другими проверками; цифры не являются
изолированным сравнением производительности. Модели остаются в памяти между
запросами; первая проверка после перезапуска процесса остаётся холодной.

Рабочий Docker обновлён с сохранением тома и сессии. Во встроенном браузере
дважды распознан уже сохранённый пользовательский снимок, без нового кадра
и физических команд ТВ: первый запрос 18,92 с, прогретый — 11,43 с.
Снимок экрана .local/ocr-warm-live.png остаётся локальным и не включается в Git.

## Исправление: прогрев до первого запроса

Ранее процесс сохранял модели только после успешного реального запроса. Теперь производственная точка входа включает обязательный предварительный прогрев до HTTP-listen: синтетический кадр с текстом проходит обычный протокол детекции и распознавания. Проверены отдельный тайм-аут 120 секунд, повторное использование процесса, отсутствие допуска реального задания во время прогрева, остановка процесса при тайм-ауте, ожидание прогрева в runtime и освобождение ресурсов при ошибке. 31 проверка recognizer/runtime прошла; API собирается. Обычный лимит 30 секунд и обработка отмены сохранены.

Рабочий Docker обновлён с сохранением тома данных и порта. Реальные startup-события подтвердили `OCR_WARMUP_STARTED` → `OCR_WARMUP_READY`, длительность 7929 мс; после готовности Python-процесс оставался запущен. Healthcheck прошёл.

В рабочей вкладке повторно распознан прежний снимок 1680×945 без нового захвата: успешно за 12,96 с вместо предыдущего тайм-аута. В результате присутствуют «Моё кино» и «Мои подписки»; известное склеивание «Историяпросмотров» сохраняется. Реальное свидетельство хранится локально вне Git.

# Выбор локального OCR для условий шага

Дата: 2026-10-18. Проверка только на синтетических экранах, без камеры и команд ТВ.

## PaddleOCR

Изолированный Docker ARM64: PaddleOCR 3.2.0, PaddlePaddle 3.2.0,
PP-OCRv5_server_det и eslav_PP-OCRv5_mobile_rec. ARM64 wheel доступен,
образ собирается и модели загружаются. При офлайн-распознавании положительного
синтетического кадра процесс завершается SIGSEGV (exit 139). Повтор с
`enable_mkldnn=False` даёт тот же результат. Модель явно выбиралась по её имени;
до этого проверка выявила несовпадение имени и каталога модели.

Для текущей реализации PaddleOCR не выбран: рабочее распознавание в целевом
контейнере не подтверждено. Исследовательский Dockerfile сохранён отдельно;
в продуктовый образ PaddleOCR не входит.

## Tesseract

Выбран существующий в проекте tesseract.js 7.0.0 с пакетами языковых моделей
rus/eng 1.0.0 (данные 4.0.0). Модели устанавливаются при сборке; во время OCR
используются локальные файлы. Один дочерний процесс на кадр, тайм-аут 30 секунд,
без повторов и без автоматического переключения на другой движок.

Набор: тёмные JPEG 1280×720, шрифт Noto Sans 40 px, надписи «Мое кино»,
«Мои подписки», «Settings». Проверены: все три надписи, одна русская отсутствует,
обе русские отсутствуют, пустой кадр, слова «Мое»/«кино» в разных областях,
повреждённый JPEG. Ожидаемые результаты получены для всех шести случаев при
локальном запуске и в ARM64-образе приложения с `--network none`. Раздельные слова не дали ложного совпадения «Мое кино».

Это проверка интеграции и простого синтетического набора, а не оценка точности
на реальных кадрах камеры. Пользовательские шрифты, блики, размытие и мелкие
надписи требуют отдельной аппаратной приёмки. Отсутствие распознанной надписи
даёт отрицательный результат условия по согласованному контракту.

Воспроизведение после сборки:

```sh
node tools/visual-checks-probe/ocr-runtime/fixtures.mjs .local/ocr-fixtures
node tools/visual-checks-probe/ocr-runtime/check-ocr.mjs .local/ocr-fixtures
```


## Дополнительная проверка 2026-10-19: лёгкая модель

PaddleOCR 3.2.0 и PaddlePaddle 3.2.0, детектор `PP-OCRv5_mobile_det`,
распознавание `eslav_PP-OCRv5_mobile_rec`. Проверены сохранённые реальные
кадры до и после настройки фокуса; изображения и результаты с пользовательскими
данными остаются локальными и не включаются в репозиторий.

На macOS ARM64 новый кадр обработан трижды без падений: 5.075, 5.261 и
5.047 секунды, без учёта загрузки моделей. Найдены «Моё кино», «Мои подписки»
и «Настройки». «История просмотров» распознана как «Историяпросмотров» и
не проходит действующее строгое сравнение. Тяжёлая модель на этом же кадре
заняла 18.555 и 41.562 секунды; на старом кадре дважды завершилась exit 139.
Поэтому исходное падение нельзя объяснить только наличием Docker.

В отдельном Linux ARM64 Docker-контейнере лёгкая модель с параметрами CPU
по умолчанию завершилась SIGSEGV (exit 139) на синтетическом кадре после
успешной загрузки локальных моделей. При `enable_mkldnn=False, cpu_threads=1`
весь набор завершился exit 0: синтетический кадр 3.830 секунды, новый реальный
кадр 14.896 секунды, старый реальный кадр 15.057 секунды. Оба реальных кадра
дали «Моё кино», «Мои подписки» и «Настройки», но склеили «Историяпросмотров».
Ограничения контейнера: 4 CPU, 4 GiB, сеть отключена, входы и модели только
для чтения. Эти времена не являются чистым сравнением macOS и Docker:
различаются режим CPU и ограничения ресурсов.

Подтверждена рабочая комбинация двух CPU-настроек, но их влияние не разделено
отдельным экспериментом; точная причина SIGSEGV не установлена. Проверка
не меняет продуктовый OCR, тест-кейсы, рабочий контейнер или правила сравнения.


### CPU-потоки лёгкой модели в Docker

На том же кадре после фокусировки, без MKL-DNN, при ограничении контейнера
4 CPU / 4 GiB: два потока — 11.816 и 11.639 секунды; четыре потока — 10.158
и 10.167 секунды (округлённо 10.2 с). Все четыре распознавания завершились
exit 0. Список распознанных строк совпал с однопоточным результатом.
Измеряется обработка кадра после загрузки моделей; режимы запускались
последовательно, по два кадра в одном процессе. На этом наборе четыре
потока ускоряют обработку относительно одного (14.448 с), но ускорение
не линейное. Это небольшой эксперимент на одной машине и одном кадре,
а не гарантия стабильности или производительности на всех установках.


Продуктовая замена: PaddleOCR mobile, четыре CPU-потока, MKL-DNN выключен.
См. `docs/development.md` для подготовки нативного окружения. Исторические
проверки Tesseract выше сохранены как основание решения, а не текущая конфигурация.


## Приёмка продуктовой замены 2026-10-19

Проверены 505 тестов API, сборка проекта, проверка типов и два браузерных
сценария с реальным PaddleOCR (положительный и отрицательный результат).
В продуктовом образе под штатным пользователем и без сети прошли все шесть
синтетических случаев: положительный, одна/обе надписи отсутствуют, пустой
кадр, слова в разных блоках и повреждённый JPEG. Оба сохранённых реальных
кадра прошли через Node.js → Python → Paddle → строгий matcher за 12.182 и
11.566 секунды с условиями «Моё кино», «Мои подписки», «Настройки».

Штатный Docker-smoke подтвердил непривилегированный runtime, HTTP, SQLite,
интерфейс, сохранение данных/сессий/ключей при пересоздании, Origin-защиту,
Compose и явные ошибки при недоступном хранилище или отсутствии ключа.
Приложение обновлено с сохранением существующего тома; интерфейс проверен
во встроенном браузере. Физический прогон ТВ при этой замене не выполнялся.
Технический предел OCR остаётся 30 секунд; дополнительные паузы и повторы
не добавлялись. Прежние отчёты не переоцениваются.

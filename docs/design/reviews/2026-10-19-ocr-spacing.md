# Проверка пробелов PaddleOCR

Дата: 2026-10-19. Исследование на двух сохранённых реальных кадрах и
синтетическом контрольном кадре. Рабочее приложение и matcher не менялись.
Изображения и полные результаты остаются локальными, в репозиторий не входят.

Окружение: продуктовый ARM64 Docker-образ, сеть отключена, 4 CPU / 4 GiB;
PP-OCRv5_mobile_det + eslav_PP-OCRv5_mobile_rec, MKL-DNN выключен,
4 CPU-потока. Времена включают predict, без загрузки моделей.

Поддержка символа пробела в CTC-декодере используемой версии уже включена.
Изменение отступов детектора (text_det_unclip_ratio) проверено на обоих кадрах:

- 1.5 (базовый): 10.7–11.0 с; «Историяпросмотров» склеена на обоих.
- 1.0: 11.4–12.6 с; склеивание осталось, дополнительно склеились «Моиподписки».
- 1.25: 10.4–10.9 с; проблема осталась.
- 2.0: 9.2–10.4 с; исправлен только старый кадр, новый остался со склеиванием.

Внутренний статический размер входа распознавателя text_rec_input_shape
(снимок не менялся, второго прохода не было):

- [3,48,480]: 12.1–12.5 с; склеивание осталось на обоих реальных кадрах.
- [3,48,640]: 14.9–16.0 с, повтор нового кадра 14.9 с. «История просмотров»
  восстановлена на обоих; «Моё кино», «Мои подписки», «Настройки» сохранены.
  Синтетический положительный кадр также читается. Однако ухудшились другие
  строки: на новом кадре «Помощь» превратилась в «Помошь», WINK — в «ушК».
- [3,48,960]: на новом кадре 21.3 с; целевой пробел восстановлен, но испорчены
  «Моё кино» и «Мои подписки». Не подходит как общее улучшение.

Вывод: простой глобальной настройки без потери качества на проверенном наборе
не найдено. Ширина 640 помогает конкретной надписи ценой дополнительных 4–5 с
и регрессий других строк. Не включать её глобально. Следующий эксперимент:
отдельное распознавание проблемной строки с сохранением базовых результатов;
его точность, выбор строки, ложные совпадения и стоимость ещё не проверены.


## Адресная перепроверка строки

Следующий эксперимент выполнен на тех же двух кадрах, в том же Docker-образе
без сети. После базового OCR для ненайденного условия выбирался только блок,
совпадающий с ожидаемой надписью после удаления пробельных символов и обычной
нормализации регистра/NFC. Это сравнение использовалось только для выбора
кандидата, не для успешного результата.

Строка вырезалась из исходного кадра штатным CropByPolys по соответствующему
rec_polys. Выполнялось только TextRecognition с той же моделью и входом
[3,48,640], без повторного детектора. Базовые строки сохранялись. Для нескольких
условий с одним кандидатом результат перепроверки использовался повторно.

Оба кадра дали «История просмотров» с правильным пробелом. Новый кадр:
базовый OCR 10.666 с, дополнительно 0.442 с (из них создание второго
распознавателя 0.108 с и inference строки 0.333 с). Старый кадр: базовый OCR
10.744 с, дополнительно 0.302 с, включая inference строки 0.301 с;
распознаватель уже был загружен в том же исследовательском процессе.

Контрольные условия на каждом кадре:

- «История просмотров» прошла только после точного повторного распознавания.
- «Настройки» прошли по базовому результату, без повторного распознавания этой строки.
- «Несуществующая надпись» не получила кандидата и осталась неуспешной.
- «Истори япросмотров» получила того же кандидата, но не прошла: повторный
  OCR вернул другую расстановку пробелов. Удаление пробелов не даёт успех само по себе.
- На кадр обработана одна дополнительная область, в том числе при двух
  условиях-кандидатах; повторное использование результата не меняло вердикт.

Это подтверждает работоспособность идеи на двух известных кадрах, а не общую
точность. Производственная интеграция ещё не выполнена: текущий контракт
исполнителя принимает только изображение и не возвращает координаты наружу.
Для реализации нужно спроектировать передачу условий/координат, границы
времени и числа дополнительных областей и регрессионные проверки, сохранив
отмену, строгий matcher и происхождение результата.

## Продуктовая интеграция

Адресная перепроверка подключена через двухэтапный внутренний протокол:
Node.js выбирает индексы по существующему matcher и сравнению без пробелов,
Python сохраняет исходный кадр и координаты и возвращает до трёх дополнительных
строк. Базовые строки обязательны и не изменяются. Повторные кандидаты
обрабатываются один раз. Не запрошенные области или изменение базовых строк
считаются некорректным ответом исполнителя. Формат тест-кейсов и отчётов
не менялся; использование второго этапа отмечается суффиксом модели
`+line-retry-640`.

Проверено 509 тестов API, затем дополнительно тест общего тайм-аута (все 16
тестов исполнителя прошли), проверка типов и два браузерных сценария с Paddle.
В продуктовом образе без сети на старом и новом фото «История просмотров»
прошла строгое сравнение после перепроверки; ошибочное «Истори япросмотров»
и отсутствующая надпись остались неуспешными. Основная строка
«Историяпросмотров» сохранена. В варианте только с условием «Настройки»
второй этап не использовался (36 исходных блоков вместо 37 с перепроверкой).
Полное время через Node.js, включая загрузку Python/моделей: 19.155 и 13.564 с
с перепроверкой, 12.370 с без неё. Эти отдельные измерения не изолируют
накладные расходы этапа; для их оценки выше приведён отдельный эксперимент.
Общий технический предел 30 секунд и отмена процесса сохранены.

# Разработка и запуск без Docker

Нужны Node.js 22.12+ и pnpm 11.15.1. Из корня репозитория:

```sh
pnpm install
pnpm build
export REMOTE_WEBOS_DATA_DIR="$(pwd)/.local/data"
export REMOTE_WEBOS_HOST=127.0.0.1
export REMOTE_WEBOS_PORT=8080
export REMOTE_WEBOS_PUBLIC_ORIGIN=http://127.0.0.1:8080
pnpm --filter @remote-webos-tv/api setup-token
pnpm --filter @remote-webos-tv/api start
```

Откройте адрес из `REMOTE_WEBOS_PUBLIC_ORIGIN`, введите одноразовый токен и создайте владельца. Токен действует 15 минут; новый заменяет предыдущий. После создания владельца токены больше не выдаются. Не публикуйте токен.

CLI и сервер должны использовать один абсолютный `REMOTE_WEBOS_DATA_DIR`. Каталог содержит SQLite, `auth-master.key` и `tv-master.key`: ограничьте доступ и сохраняйте весь комплект при резервном копировании. Не запускайте два сервера с одной SQLite.

## Конфигурация

Обязательные переменные показаны в примере запуска. `REMOTE_WEBOS_PUBLIC_ORIGIN` — точный origin браузера без пути и завершающего `/`; страница и API работают на одном origin.

Необязательные параметры:

- `REMOTE_WEBOS_SECURE_COOKIES` — `true` или `false`; по умолчанию `true` для HTTPS. Для HTTPS отключить Secure нельзя.
- `REMOTE_WEBOS_TRUSTED_PROXY` — IP/CIDR доверенных прокси через запятую. Без него заголовки переадресации не считаются доверенными.
- `RUN_ARTIFACT_MAX_BYTES` — квота JPEG раннера в байтах, положительное целое число; по умолчанию 1 GiB.
- `REMOTE_WEBOS_RECOVERY_TIMEOUT_MS` — общий срок восстановления от 1000 до 300000 мс, по умолчанию 60000.

Для HTTPS настройте TLS на reverse proxy, внешний origin и только действительно доверенные адреса прокси. Без HTTPS используйте локальный или доверенный сегмент сети.

## Проверки

```sh
pnpm build
pnpm typecheck
pnpm test
pnpm --filter @remote-webos-tv/web exec playwright install chromium
pnpm --filter @remote-webos-tv/web test:e2e
```

Сначала нужна свежая сборка: браузерные фикстуры импортируют собранные API/webOS. Для тестов нужны разрешённые локальные сокеты и Chromium. Используются временные данные и синтетический ТВ, не пользовательский аккаунт и не настоящий телевизор. Артефакты находятся в игнорируемом `.local/playwright`.

GitHub CI проверяет сборку, типы, модульные, интеграционные и браузерные сценарии. Автоматические проверки не доказывают физическую реакцию ТВ; протокольные и автоматические результаты находятся в [отчёте совместимости](compatibility/lg-43up76906le-webos-6.5.3.md).

Синтетические ручные проверки в общем браузере должны использовать другой hostname или отдельный профиль. Cookies не разделяются по портам; тестовый вход на том же hostname заменяет cookie активного приложения.

### Локальный OCR (PaddleOCR)

Автоматические текстовые условия используют Python 3.11, PaddleOCR 3.2.0,
PaddlePaddle 3.2.0 и две локальные модели: `PP-OCRv5_mobile_det` и
`eslav_PP-OCRv5_mobile_rec`. В Docker они устанавливаются при сборке и
проверяются по SHA-256. Во время распознавания скачивание моделей не требуется.

Для разработки без Docker создайте отдельное Python-окружение, установите
`apps/api/src/ocr/requirements.txt`, задайте `PADDLE_PDX_CACHE_HOME` для каталога
кэша и выполните `apps/api/src/ocr/package-models.py` этим Python. Первичная
подготовка требует сети. Перед запуском API задайте:

- `REMOTE_WEBOS_OCR_PYTHON` — путь к Python этого окружения (по умолчанию `python3`).
- `REMOTE_WEBOS_OCR_MODELS` — каталог `official_models` внутри подготовленного кэша.

OCR использует один постоянный процесс с 4 CPU-потоками и отключённым
MKL-DNN. Процесс загружается при первом запросе; успешные запросы сохраняют
модели в памяти. Повторное распознавание не загружает их заново. Первая
проверка после запуска или перезапуска процесса остаётся холодной. Сохраняются технический тайм-аут 30 секунд, отмена процесса и строгие
правила сравнения надписей. Отсутствующая модель или зависимость — техническая
ошибка шага; автоматического возврата к Tesseract нет. Прежние отчёты сохраняют
исходный идентификатор движка.

При ненайденном текстовом условии сервер может запросить адресную перепроверку:
совпадение всей строки без пробелов выбирает кандидата, но не означает успех.
Второй распознаватель обрабатывает до трёх выбранных областей с входом
`[3,48,640]`, без повторного детектора. Одна область обрабатывается один раз,
даже если подходит нескольким условиям. Уже найденные условия и отсутствие
кандидата не требуют второго прохода. Базовые строки сохраняются, результаты
перепроверки добавляются к ним и проверяются тем же строгим matcher.
В идентификаторе модели использованной перепроверки появляется
`+line-retry-640`. Общий тайм-аут 30 секунд охватывает оба этапа.

Внутренний Python-протокол: строка JSON `id, imageBytes`, затем ровно
указанное число байт изображения; ответ `id, phase: base`; запрос
`id, retryIndices`; итоговый ответ `id, phase: result`. stdin остаётся открытым
для следующего запроса. Один процесс обслуживает только один снимок одновременно;
идентификатор защищает от смешивания ответов. При отмене, превышении срока,
сбое или нарушении протокола процесс уничтожается; до его завершения занятость
не снимается. Следующий запрос создаёт новый процесс. Остановка приложения
завершает и простаивающий процесс. Текст условий остаётся в Node.js, координаты — в Python.

### Пробная проверка камеры и OCR

«Телевизоры → выбранный ТВ → Проверить распознавание» использует существующий захват и
выравнивание экрана. Кнопка «Распознать текст» каждый раз получает свежий кадр
и распознаёт его; снимок показан слева, текст справа (на узком экране — ниже). Запрашиваемые 1920×1080 или 1280×720 и источник сохраняются
в localStorage браузера; доступное разрешение может отличаться от запроса,
изображение не увеличивается. На другом браузере выбор настраивается заново.

`POST /api/camera/ocr` принимает JPEG до `MAX_SNAPSHOT_BYTES` с текущей сессией,
Origin и CSRF. Ответ — блоки текста, engine, model и elapsedMs; проба не
сохраняется как запуск или артефакт. Используется общий OCR-процесс: при
занятости возвращается 429 OCR_BUSY, при превышении срока — 504 OCR_TIMEOUT,
при техническом сбое — 503 OCR_FAILED. До 10 проб в минуту; срок OCR 30 секунд.
Запрос отменяется при отключении клиента, отзыве сессии и остановке сервера.
Найденный текст — сырой результат OCR, а не подтверждение условий теста.
Проба размещена под существующей камерой, без второго потока. Закрытие блока
отменяет запрос и очищает пробу; просмотр камеры продолжается.

### Предварительный прогрев OCR

Рабочий сервер до открытия HTTP запускает общий OCR-процесс и выполняет синтетическое распознавание (детектор и распознаватель). Готовность записывается событием `OCR_WARMUP_READY` с `durationMs`; начало — `OCR_WARMUP_STARTED`. Модели остаются в том же процессе для первого реального снимка. На прогрев выделено 120 секунд, обычный запрос по-прежнему ограничен 30 секундами. Ошибка прогрева останавливает запуск с очисткой ресурсов; приложение не объявляет готовность с холодным OCR. Docker healthcheck допускает этот период запуска. После аварии или отмены реального задания процесс по-прежнему уничтожается: следующий запрос может оказаться холодным; автоматическое восстановление прогрева после такой ошибки отдельно не реализовано.

Пробный OCR принимает только JPEG, прошедший общую проверку снимков: до 5 MiB и не более 4096×4096 пикселей. Повреждённые кадры и превышение разрешения отклоняются с `400 INVALID_SNAPSHOT` до декодирования OCR.

# Philips Whale: подключение и базовый пульт

Дата: 2026-10-20.
Статус: проект для согласования перед планом реализации.

## Цель и границы

Добавить Philips/Whale в существующее приложение: выбор платформы, IP,
сопряжение по PIN с экрана ТВ, сохранение авторизации, переподключение и
базовые команды существующего пульта. Пользователь согласовал этот объём
после проверки физического Philips 43PUS7608/60 с Whale 2.0.

Реализация использует текущий сервер и Docker-развёртывание. Будущая
архитектура веб-сервиса с локальным агентом остаётся отдельной задачей;
сетевой адаптер не зависит от браузера и пригоден для переноса в агент.

Не входят: запуск приложений, перечисление входов, текстовый ввод,
указатель, удержание кнопок, выключение, пробуждение и автообнаружение.
Поддержка всех моделей Whale не заявляется по результату одного устройства.

## Проверенные факты

На физическом устройстве в этой сессии:

- HTTP 1925 и HTTPS 1926 возвращают `/system` и `/6/system` с HTTP 200.
- `api_version` равна 6.1.0; `pairing_type` — `digest_auth_pairing`;
  `secured_transport` — true; `os_type` — Linux.
- Модель и прошивка передаются в полях `model_encrypted` и
  `softwareversion_encrypted`; открытые значения не проверены.
- `POST /6/pair/request` вернул `SUCCESS`, временный ключ, timestamp и
  `timeout: 30`; на ТВ появился PIN.
- `POST /6/pair/grant` с Digest-авторизацией и корректной подписью вернул
  HTTP 200 и `{"error_id":"SUCCESS","error_text":"Pairing completed"}`.
- Авторизованный `GET /6/powerstate` вернул `{"powerstate":"On"}`.
- `POST /6/input/key` с `{"key":"CursorRight"}` вернул HTTP 200 и
  HTML `Ok`; пользователь подтвердил перемещение фокуса на экране.
- Ошибки `TIMEOUT` и `INVALID_PIN` также приходили с HTTP 200.

PIN, IP, идентификаторы и ключ устройства в документацию и тесты не включаются.
Whale 2.0 — версия ОС, сообщённая пользователем. Версия API 6.1.0 не является
версией ОС и не записывается вместо неё.

## Выбранный подход

Отдельный пакет `packages/philips`, реализующий существующий `TvAdapter`.
В контрактах платформа называется `whale`, в интерфейсе — «Philips Whale».
Это ограничивает заявленную поддержку проверенной платформой, хотя пакет
реализует протокол Philips/jointSPACE v6.

Альтернативы: расширить LG-адаптер либо вызывать внешний инструмент.
Они отклонены: у LG другой протокол и жизненный цикл, а внешний процесс
усложнит отмену, хранение ключей и диагностику. Новый адаптер использует
общие серверные операции, шифрование, реестр устройств и маршруты команд.

## Контракт сопряжения

Текущий `PairingRequest` расширяется необязательным асинхронным callback
запроса PIN. LG/Samsung его не вызывают. Callback получает срок действия
запроса и ожидает PIN либо отмену. Сам адаптер владеет временным ключом,
timestamp, идентификатором клиента и протокольной подписью.

В `TvOperation` добавляется необязательный публичный challenge: тип `pin`
и `expiresAt`. Он существует только в активной операции. Это аддитивное
расширение схемы; действующие статусы и семантика LG/Samsung сохраняются.

Новый защищённый маршрут:

`POST /api/tvs/:tvId/operations/:id/pin`, тело `{"pin":"1234"}`.

- Проверяется ровно четыре ASCII-цифры, включая ведущие нули.
- Только актуальная операция этого устройства с ожидающим challenge.
- Проверка действующей сессии, владельца операции, CSRF и лимита попыток
  выполняется до передачи кода адаптеру.
- Принятый код возвращает 202 и текущую операцию; успех устанавливается
  только после ответа ТВ и авторизованного чтения состояния.
- Повторная одновременная отправка не вызывает второй сетевой запрос.
- Чужой, отменённый, завершённый или уже истёкший запрос не принимает PIN.
- Код, ключ и auth-заголовки исключаются из журналирования запросов.

Срок ожидания — минимум из срока, указанного ТВ, и общего бюджета операции.
Отмена, удаление ТВ, закрытие сервиса и выход владельца снимают ожидание и
отменяют сетевую работу. Поздний ответ не сохраняет авторизацию.
Неправильный/просроченный PIN завершает текущую попытку с конкретной ошибкой;
новый PIN вызывается только явным повтором пользователя. Автоповтора POST нет.

## Протокол и безопасность

Управление и сопряжение выполняются по HTTPS 1926, префикс `/6/`.
Порты и префикс — протокольные константы; адрес берётся из существующей
валидации буквального RFC1918 IPv4. Перенаправления на другие адреса запрещены.

Самоподписанный сертификат обрабатывается внутри этого адаптера, без
глобального отключения TLS. При первом сопряжении сертификат фиксируется
на срок операции, PIN подтверждает доступ к физическому ТВ; fingerprint
сохраняется вместе с авторизацией. При переподключении требуется совпадение
сертификата. Замена сертификата приводит к явной ошибке и повторному
сопряжению. Подключение по новому IP сохраняет эту проверку.

Подпись: HMAC-SHA1 от UTF-8 конкатенации timestamp и PIN с протокольным
общим ключом; Base64 кодирует байты HMAC, а не текст hex. Общий ключ —
константа протокола, не пользовательский секрет. Нужен фиксированный
синтетический тест-вектор, воспроизводящий найденную ошибку формата подписи.

Digest-авторизация реализуется в транспортном модуле с проверкой реального
challenge: realm, nonce, algorithm, qop, URI и nonce count. Проверить поведение
сервера для stale nonce. Не допускается отправка пользовательского ключа
на другой origin. До выбора зависимости проверить существующие зависимости;
не добавлять библиотеку без проверки её поведения на реальном challenge.

HTTP 200 не означает успех: JSON `error_id` проверяется отдельно. `INVALID_PIN`,
`TIMEOUT`, `CONCURRENT_PAIRING`, отказ авторизации, неверная структура и сетевой
сбой получают раздельные безопасные сообщения. Для команды допускается
проверенный ответ HTML `Ok` и документированная успешная пустая форма;
произвольный HTML или неизвестный JSON не считается подтверждением.

## Авторизация, идентификация и хранение

Credential адаптера — версионированная строковая JSON-структура с client id,
auth key и fingerprint. Её валидирует адаптер; существующий серверный cipher
шифрует структуру целиком. В API и браузер она не передаётся.

Сохранение проходит через текущий staging и repository только после успешного
grant, проверки состояния, проверки отмены и метаданных. Сбой новой попытки
не заменяет ранее сохранённый ключ. Обычный reconnect использует сохранённую
авторизацию и не вызывает PIN автоматически.

Расшифровка полей модели/прошивки следует фактическому формату Philips AES-CBC,
проверяется на синтетических векторах и на физическом ответе без вывода
идентификаторов. Серийный номер не требуется и не извлекается. При отсутствии
модели допустимо явное имя «Philips Whale» с отсутствующей версией, без
придуманной модели или подстановки версии API вместо ОС. Повреждённое поле
диагностируется; ошибка не маскируется фиктивным значением.

Добавляется последовательная миграция ограничения `tv_devices.platform`.
Существующие строки, default TV, порядок, ссылки тестовых прогонов и
зашифрованные credentials сохраняются. Старые миграции не редактируются.

## Пульт и остальные потребители платформы

`readSnapshot` подтверждает доступность закреплённого TLS-устройства через `powerstate`.
Дополнительные данные, например громкость, не являются условием подключения.
`prepareRemote` проверяет готовность авторизации; `sendButton` делает один
авторизованный POST. Потеря ответа после отправки не вызывает повтор команды.

Базовая таблица включает направления, подтверждение, Home, Back, меню,
громкость, mute, каналы, цифры, цветные кнопки и воспроизведение только при
однозначном соответствии протоколу. Неподдерживаемая кнопка даёт явную
ошибку возможности; подмена EXIT на Back или PLAY на toggle без проверки
семантики запрещена. До объявления всей группы кнопок необходимо проверить
контракт отображения неподдерживаемых действий в общем пульте.

Первый профиль: `buttons: true`, остальные возможности false, включая
`ssap`, `pointer`, `apps`, `inputs`, `textInput`, `powerOff`, `wakeOnLan`.
Объявленные ТВ возможности сами по себе не включают нереализованные функции.
Удержание отключено; одиночные нажатия доступны и в существующем раннере.

Проверяются все потребители `TvPlatform`: factory, repository, устройства,
подписи платформ, каталог действий/удержаний, команды, capability gating,
контракты и хранение отчётов запусков. Локальный enum в `test-runs` заменяется
канонической схемой платформы, чтобы история могла прочитать Whale-прогон.

## Интерфейс

Существующая форма добавления получает «Philips Whale». После отправки IP
показывает поле «PIN с экрана телевизора», оставшееся время, подтверждение
и отмену. На неверный код/таймаут — конкретная ошибка и явный новый запрос.
PIN очищается после отправки, отмены и закрытия; в storage/history не пишется.
Сопряжение и повторное сопряжение используют один компонент PIN.

Поле использует текстовый ввод с numeric input mode и ограничением длины,
сохраняя ведущие нули. Есть постоянная подпись, клавиатурная отправка и
фокус на появившемся поле; ошибка доступна для assistive technology.
Счётчик не озвучивается каждую секунду. Состояния кнопок исключают двойную
отправку. Компоновка, размеры, палитра и тема следуют ТЗ от 2026-10-11 и
текущим общим компонентам; отдельного редизайна экранов нет.

Недоступные приложения/питание не отправляют команды. На экранах настроек,
списка, управления и отчётов платформа подписана корректно. Проверка UI —
встроенный браузер, обе темы, клавиатура, ошибки и таймаут на синтетическом
стенде; затем итоговая Docker-сборка и осмотр работающего приложения без
удаления volumes и без потери пользовательских правок.

## Проверка и критерии приёмки

1. Синтетический транспорт: подпись, Digest, изменившийся сертификат,
   HTTP 200 с ошибкой, malformed JSON, неизвестный HTML, timeout и abort.
2. Lifecycle: PIN с ведущим нулём, неверный формат, неправильный PIN,
   истечение срока, отмена, два submit, чужая сессия, поздний grant,
   сбой шифрования/записи. В каждом случае ключ не утекает и не сохраняется
   после отмены; старое устройство остаётся доступным для восстановления.
3. Миграция с LG/Samsung: данные и default/order сохраняются; Whale
   сохраняется и читается после перезапуска, старая история читается.
4. API/UI: весь путь IP → challenge → PIN → available, repair,
   reconnect без PIN, каталог/кнопки и отображение платформы в отчёте.
5. Фокусные регрессионные тесты LG/Samsung, затем typecheck и build;
   более широкие проверки — по найденному риску.
6. Физический ТВ: сопряжение уже из приложения, перезапуск и reconnect,
   одно согласованное нажатие с подтверждением пользователя. Остальные
   физические команды выполняются только в согласованном объёме.

Доставка HTTP-команды и результат на экране учитываются отдельно.
Синтетические проверки не выдаются за проверку физического устройства.

- Общий интерфейс: `packages/tv-adapter/src/index.ts`.

- Создание адаптеров: `apps/api/src/runtime.ts`.
- Хранение: `apps/api/src/tv/repository.ts`, `apps/api/src/storage/migrations.ts`.
- UI: `apps/web/src/pages/AddTv.tsx`, `apps/web/src/pages/TvSetup.tsx`.
- Актуальная подпись: https://github.com/danielperna84/ha-philipsjs/blob/master/haphilipsjs/__init__.py
- API v6 pairing reference: https://github.com/suborb/philips_android_tv
  (старый пример содержит несовместимый формат подписи; не копировать).

На момент подготовки рабочий `main` отстаёт от origin/main на пять коммитов
и содержит несвязанные пользовательские изменения. Перед реализацией
нужно сравнить актуальную базу и изолировать изменения без потери текущих
файлов; не делать reset/stash/перенос пользовательских правок автоматически.

## Уточнение по реальному устройству после реализации

Новый Node HTTPS-транспорт проверен чтением `/6/system`; расшифровка полей
модели и прошивки прошла. На проверенной прошивке информационные маршруты
`powerstate`, `system`, `audio/volume`, `activities/current` и `context`
доступны без Digest challenge. Успешный reconnect подтверждает доступность
ТВ с закреплённым сертификатом и наличие сохранённого результата сопряжения,
а не независимое принятие ключа информационным маршрутом. Digest отправляется
там, где ТВ отвечает challenge. Поведение отозванного ключа на физическом
ТВ ещё требует отдельной проверки; оно не считается проверенным по чтению статуса.

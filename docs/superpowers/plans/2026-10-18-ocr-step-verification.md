# OCR Step Verification Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans for inline execution, or superpowers:subagent-driven-development if explicitly selected by the user. Steps use checkbox syntax for tracking.

**Goal:** Проверять обязательные надписи на одном снимке шага и останавливать тест при их отсутствии.

**Architecture:** Сервер проверяет последний сохранённый снимок шага через локальный OCR. Условия принадлежат версии кейса, результаты — запуску; следующий шаг запрещён до результата. Браузер сохраняет существующий порядок команд, пауз и снимков.

**Tech Stack:** TypeScript, Zod, Fastify, SQLite, React, Vitest, Playwright, Docker; OCR-движок выбирается проверкой в задаче 1.

**Spec:** `docs/superpowers/specs/2026-10-18-ocr-step-verification-design.md`.

## Global Constraints

- Не добавлять паузу шага, дополнительные снимки, повторные OCR-попытки или ожидание появления текста.
- После каждого нажатия сохраняется существующий снимок; OCR получает только последний снимок шага. Без нажатий — один снимок сразу.
- Все условия должны совпасть на одном кадре. Нет совпадения — `failed`, ошибка обработки — `error`.
- Старые кейсы без условий сохраняют поведение; исторические запуски не пересчитываются.
- OCR локальный; изображения, условия и распознанный текст не попадают во внешние сервисы и общие логи.
- Не более 20 надписей на шаг, от 1 до 200 Unicode-символов после trim.
- Общие компоненты, токены и защита несохранённых изменений; встроенный браузер и синтетические данные для проверки.
- Существующие изменения пользователя не коммитить и не изменять; не отправлять команды реальным ТВ без отдельного разрешения.

## Review Focus

- Поздний ответ OCR после остановки не меняет итог запуска (задача 4).
- Одинаковые слова из разных блоков не собираются в ложную фразу (задача 2).
- Повтор загрузки снимка после обрыва связи не запускает второй OCR (задача 4).
- Условия шага без нажатий исполняются один раз без задержки (задачи 4, 6).
- Смешанный кейс не выдаёт непроверенные шаги за прошедшие проверку (задача 6).

- `packages/contracts/src/text-conditions.ts` (новый): каноническая нормализация и сравнение блоков.
- `apps/api/src/ocr/` (новый): исполнитель и проверка ответа движка; без правил итогового статуса запуска.
- `apps/api/src/test-runs/service.ts`: владелец выполнения и фиксации вердиктов.
- `apps/api/src/test-runs/repository.ts`, `routes.ts`, `artifacts.ts`, `runtime.ts`: хранение, доставка, подключение и закрытие OCR.
- `apps/web/src/components/StepTextConditions.tsx` (новый), `pages/TestCaseEditor.tsx`: редактирование условий.
- `apps/web/src/pages/TestRunner.tsx`, `TestRunReport.tsx`, `TestRuns.tsx`, `run-presentation.tsx`, `useTestRun.ts`: прогресс, итог и отчёт.
- Docker и зависимости: только после выбора движка; фиксация версий и моделей.

### Task 1: Проверить и закрепить локальный OCR

**Files:** `tools/visual-checks-probe/`; выбранные зависимости и Docker-файлы определяются результатом проверки.

**Interfaces:** выход — закреплённый движок, модели, поддержанные CPU-архитектуры, реальный образец сериализованного ответа с блоками текста и команда запуска.

- [ ] Проверить актуальную официальную документацию PaddleOCR через Context7; сопоставить с существующими исследовательскими результатами. Не устанавливать незакреплённый latest.
- [ ] Собрать синтетические RU/EN кадры: обе надписи, одна отсутствует, ни одной, пустой экран, несвязанные блоки и повреждённое изображение. Не использовать реальные пользовательские сценарии/кадры.
- [ ] Проверить PaddleOCR в изолированном Docker на целевой машине: CPU, отсутствие сети при распознавании, доступность закреплённых моделей, структурированный результат, отмена процесса. Точный текст двух эталонных надписей должен распознаваться на положительных кадрах.
- [ ] При несовместимости проверить уже принятый исследовательский Tesseract с rus+eng на тех же кадрах и явно сравнить качество; смену основного кандидата обосновать результатами.
- [ ] Сохранить краткий отчёт без приватных данных. По реальному формату ответа уточнить файлы исполнителя и Docker-инструкции в этом плане; если ни один движок не проходит положительные кадры — не продолжать интеграцию с фиктивным OCR.

### Task 2: Контракты и единые правила совпадения

**Files:** `packages/contracts/src/test-cases.ts`, `test-runs.ts`, `index.ts`; новые `src/text-conditions.ts`, `test/text-conditions.test.ts`; существующие `test/test-cases.test.ts`, `test/test-runs.test.ts`.

**Interfaces:** `textConditions?: string[]` у шага; `OcrBlock={text:string}`; `matchTextConditions(expected:string[],blocks:OcrBlock[]):{expected:string;found:boolean}[]`. Необязательный `verification` на последнем item: `{status:'passed'|'failed',conditions,recognizedBlocks,engine,model,checkedAt,snapshotSha256}`. `verificationState?:'pending'|'running'` на проверяемом item. Новые статусы запуска `passed`, `failed`; стадия ошибки `ocr`.

- [ ] Написать регрессии: старый кейс без поля читается; 20 строк принимаются, 21 отвергается; пустая строка и 201 символ отвергаются; emoji считаются Unicode-символами. Запустить до реализации и подтвердить отказ на новых данных.
- [ ] Написать таблицу сравнения: NFC, регистр, повторные пробелы; е/ё различаются; «кино» не совпадает с «кинотеатр»; «Мое кино» не собирается из разных блоков; все/часть/ноль совпадений.
- [ ] Реализовать единую нормализацию и поиск непрерывной последовательности слов внутри одного блока, без fuzzy-поиска. Экспортировать из контракта; не дублировать на сервере.
- [ ] Добавить схемы результата и состояний. Поля проверки необязательны для совместимости; summary исключает item-содержимое и OCR-текст.
- [ ] Проверить: `pnpm --filter @remote-webos-tv/contracts test`, затем `pnpm --filter @remote-webos-tv/contracts typecheck`. Зафиксировать только изменения задачи.

### Task 3: Изолированный OCR-исполнитель

**Files:** новые `apps/api/src/ocr/recognizer.ts`, `worker` в формате выбранного движка; `apps/api/test/ocr-recognizer.test.ts`; `apps/api/package.json`, `Dockerfile`, lockfile.

**Interfaces:** `recognize(image:Buffer,signal:AbortSignal):Promise<{blocks:OcrBlock[];engine:string;model:string}>`; `close():Promise<void>`. Исполнитель получает JPEG, возвращает проверенный ограниченный ответ; интерпретация условий остаётся в контракте.

- [ ] Написать тесты отмены до старта/во время OCR, аварийного завершения, некорректного ответа и остановки дочернего процесса. Инъекция транспорта процесса позволяет не полагаться на sleeps.
- [ ] Реализовать один активный OCR на исполнитель, технический тайм-аут 30 секунд; превышение/занятость даёт явную техническую ошибку, без очереди неограниченного размера и повторов. Ограничить ответ 1 MiB, проверить схему до использования; распознанный текст не выводить в логи.
- [ ] Подключить закреплённые модели в образ при сборке, исключить скачивание при пользовательском запуске. Для временных файлов использовать приватный каталог и cleanup при успехе/ошибке/отмене; не включать пути в публичные ошибки.
- [ ] Запустить узкие тесты исполнителя и положительные/отрицательные синтетические JPEG через реальный движок в Docker без сети. Зафиксировать изменения задачи.

### Task 4: Серверная проверка и жизненный цикл

**Files:** `apps/api/src/test-runs/service.ts`, `repository.ts`, `routes.ts`, `artifacts.ts`, `runtime.ts`; `apps/api/test/test-run-service.test.ts`, `test-run-routes.test.ts`, `test-run-storage.test.ts` (при отсутствии создать).

**Interfaces:** добавить инъекцию `recognize` из задачи 3 в зависимости сервиса. `saveSnapshot` сохраняет свидетельство и запускает проверку последнего item шага. GET запуска показывает состояние OCR; upload возвращает только после проверки. `advance` отклоняет переход, пока проверка ожидается/выполняется.

- [ ] Сначала воспроизвести тестом текущий дефект для новой функции: последний снимок завершает кейс `needs_review` без проверки условий.
- [ ] Покрыть последний/промежуточный item, шаг без нажатий, отсутствие условий, все найденные/часть/пустой OCR. При `failed` счётчик отправленных команд следующего шага равен нулю.
- [ ] После сохранения JPEG опубликовать проверяемое состояние, выполнить OCR с сигналом владельца и техническим тайм-аутом; сверить item, хеш и текущую ревизию перед записью результата. Отдельно классифицировать ошибки OCR и хранения, не расширять существующий catch хранения на OCR.
- [ ] Повторный upload с тем же хешем возвращает текущий результат или разделяет существующую pending-проверку; другой хеш сохраняет `SNAPSHOT_CONFLICT`. Наличие saved-фазы само по себе не разрешает advance.
- [ ] Через управляемый Promise проверить stop/revoke/close во время OCR и поздний ответ; освобождение lease происходит после завершения отменённой работы. Перезапуск сохраняет существующую диагностику незавершённого запуска.
- [ ] Все условия пройдены при завершении — `passed`; нет условий в кейсе — `needs_review`; первое несовпадение — `failed`; ошибка OCR — `error` со стадией `ocr`. Старые записи и история остаются читаемыми.
- [ ] Проверить аутентификацию/CSRF/rate limit существующих маршрутов, новые статусы фильтра истории и отсутствие текста в summary. Запустить API-тесты с `--maxWorkers=2`, typecheck; зафиксировать изменения задачи.

**Interfaces:** `StepTextConditions({value,onChange,disabled})`, где value — список строк. Состояние принадлежит существующему черновику шага и сохраняется теми же кнопками.

- [ ] Прочитать `apps/web/PRODUCT.md`, продуктовый UI-spec и применимые mockups; использовать Impeccable и UI UX Pro Max по AGENTS.md перед UI-работой.
- [ ] Написать тест: добавить две надписи, сохранить шаг и кейс, повторно открыть — строки сохранены; отмена выхода сохраняет несохранённые условия; пустая строка показывает конкретную ошибку.
- [ ] Добавить «Условия» после нажатий: строки «На экране есть текст», добавление/удаление, ограничение 20. Не добавлять паузу и не менять поля нажатий.
- [ ] Включить условия в dirty-check, применение шага, импорт/экспорт и сохранённую версию через общую схему. Синтетический BDD остаётся описательным текстом и не создаёт условия автоматически.
- [ ] Запустить узкие тесты редактора и компонента, web typecheck; зафиксировать изменения задачи.

### Task 6: Выполнение, отчёт, история и приёмка

**Files:** `apps/web/src/pages/TestRunner.tsx`, `TestRunReport.tsx`, `TestRuns.tsx`, `run-presentation.tsx`, `useTestRun.ts`, `run-execution.ts`, `api.ts`; соседние тесты, `test/e2e/test-runs.spec.ts`, `scripts/docker/smoke.mjs`.

**Interfaces:** потреблять состояния задачи 2 и серверный вердикт; клиент не вычисляет свой итог. Текущий алгоритм capture сохраняет число снимков и существующие паузы.
